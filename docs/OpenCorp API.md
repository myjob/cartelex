# corp search with active status and incorpartion_date
 Here's how to filter for active companies within a certain period.

There are two separate concerns to combine: the "active" status filter and the date-range restriction. They're controlled by different parameters.

**Filtering by active status.** There are two ways, and they behave differently:

- `inactive=false` — excludes any company OpenCorporates has mapped to an inactive state (dissolved, removed, liquidated, etc.). This is the broad, cross-jurisdiction option. Note the caveat in the docs: not every register publishes a status, so absence of "inactive" doesn't guarantee a company is genuinely active.
- `current_status=Active` — matches the literal status string the register itself uses. This is exact-match against the register's own vocabulary, so it's stricter but also more brittle (some registers use "Active/Compliance," "Active - In Good Standing," etc., which wouldn't match a plain "Active"). Because `current_status` is a term filter, you can pipe alternatives: `current_status=Active|Active/Compliance`.

For most "only active companies" use cases, `inactive=false` is the right choice.

**Restricting to a certain period.** This is where you need to decide what "period" means, because there's no single "was active during this window" filter. The date filters each target a specific date field:

- `incorporation_date` — when the company was incorporated
- `dissolution_date` — when it was dissolved
- `created_at` — when the record was added to OpenCorporates
- `updated_at` — when the record was last changed

Each accepts a **date range** in the form `start:end`, and either side can be omitted for an open bound. So `incorporation_date=2010-01-01:2015-12-31` means incorporated within that window, `incorporation_date=2010-01-01:` means on or after that date, and `incorporation_date=:2015-12-31` means on or before it.

**Putting it together.** For active companies incorporated in a given period:

```
https://api.opencorporates.com/v0.4/companies/search?q=YOURTERM&inactive=false&incorporation_date=2010-01-01:2015-12-31&api_token=YOURTOKEN

https://api.opencorporates.com/v0.4/companies/search?q=%22Anheuser-Busch%20Incorporated%22&inactive=false&incorporation_date=1995-01-01:1998-08-04
```

A couple of things worth flagging:

The date range filters on the field you name — it does _not_ express "active at any point during this period." If your notion of "active during 2010–2015" means "incorporated before 2015 and not dissolved before 2010," there's no single parameter for that. You'd approximate it by combining bounds, e.g. `incorporation_date=:2015-12-31` together with `inactive=false`, and possibly `dissolution_date=2010-01-01:` — but a company with no published dissolution date may or may not be caught depending on how the register reports it, so test against your jurisdiction.

Also note the deprecated parameters (`incorporated_before`, `incorporated_since`, `exclude_inactive`, etc.) still appear in the docs but you should use the new range-based fields and `inactive` instead.

The fuzzy results are expected — OpenCorporates search is loose by design, and three specific things are defeating your attempt at an exact match:

**Quotes don't do phrase matching.** OpenCorporates has no quoted-phrase operator. The `%22` characters are simply stripped as non-text characters, the same way it strips dashes, parentheses, and commas. So your term reduces to the tokens _anheuser / busch / incorporated_ — the quotes accomplish nothing.

**"Incorporated" is normalised away to a company type.** The docs note that Corp/Inc/Ltd/PLC get normalised so the long and short forms are interchangeable. "Incorporated" collapses to "Inc," which nearly every "…, Inc." entity carries — so that word adds essentially no precision.

**The matcher requires all words in any order but allows extra words.** So you effectively searched for "anheuser busch" plus a company-type token, and every subsidiary containing both words qualifies: Import Investments, Sales of Hawaii, Sales of South Bay, and so on.

Net effect: the query became "anheuser busch «inc»" with loose matching, which returns everything that fits.

- Add `fields=name` to stop matching against `normalised_name` and `previous_names`, which trims some noise.
- Retrieve results and filter client-side on the exact `name` — the reliable approach given how loose the search is.

Right — and the distinction is the whole issue. `incorporation_date` filters on the incorporation _event_ falling inside the window. "Active during the period" is a different predicate that the API has no single parameter for. But you don't have to download everything; you can usually express it with one or two targeted searches.

The logical condition for "the company existed/was active at some point during [P_start, P_end]" is:

```
incorporation_date <= P_end   AND   (dissolution_date >= P_start  OR  dissolution_date is null)
```

i.e. it was already incorporated by the end of your window, and it hadn't already been dissolved before your window began (a null dissolution date meaning still active).

The reason this doesn't collapse into one clean query is that `dissolution_date` is a date-range filter, and a date filter requires the field to be **present and in range**. So `dissolution_date=1995-01-01:` catches companies dissolved on/after that date but _silently drops every still-active company_ (null dissolution date) — which is the opposite of what you want. There's no way to say "≥ P_start OR null" in a single date filter, and no boolean OR across the query.

So the practical approach is a union of two searches:

**Query A — still-active entities that already existed by period end**

```
?q=YOURTERM&incorporation_date=:1998-08-04&inactive=false&api_token=xxx
```

**Query B — entities dissolved during-or-after the period (i.e. still alive at period start)**

```
?q=YOURTERM&incorporation_date=:1998-08-04&dissolution_date=1995-01-01:&api_token=xxx
```

Union the results and dedupe on `opencorporates_url`. That's two paginated searches instead of a full dump — modest quota cost, scaling with pages of _your_ result set rather than the whole jurisdiction.

If you actually only care about companies that existed during the window **and are still active today**, then Query A alone is enough — one search, and you can drop Query B entirely.

Several of your Delaware results have `inactive: null` and `current_status: null` — the register never published a status. `inactive=false` excludes only _known-inactive_ companies, so these null-status ones will pass through Query A. That's usually what you want (you're not wrongly dropping them), but it means "active" here really means "not known to be inactive," not "confirmed active." OpenCorporates flags this exact limitation.
