# KB_SQL Retrieval Step

The `kb_sql` tool is a critical structured query step in the `QARetrievalPipeline` (`QARetrievalPipeline` inside [retrieval_modules.py](file://~/a/celex-facts/src/pipelines/agent_dspy/retrieval_modules.py)). It enables macroscopic aggregation, counting, trend analysis, and cohort filtering across approximately 800 competition law cases stored in the structured knowledge base (`celex_facts.facts`).

---

## 1. Purpose & Routing Logic

The Q&A Planner (`QAPlannerModule`) routes to `kb_sql` when the user's natural language question involves macroscopic trends, metrics, or distributions. 

### Recommended Use Cases
* **Aggregations:** Counting cases, calculating averages, finding minimum/maximum bounds.
* **Trends:** Grouping results by decision year or sector.
* **Cohort Filtering:** Finding all cases that share a specific property (e.g., `is_court_involved = 'True'`).

### Anti-Patterns (When `kb_sql` is NOT used)
* **Free-Text Entity Search:** Looking for company names (e.g., "Koninklijke"), commissioner names (e.g., "Karel Van Miert"), or specific cities/countries in text. These exist inside unstructured document chunks and are instead routed to `doc_search`.
* **Court Judgment Content:** Querying the reasoning or ruling details of a court. The structured `court_list_raw` fact lists *which* courts were involved, but the *contents* of the rulings are in document chunks and must be searched via `rag_search_in_case` or `doc_search`.

## 2. Structured Schema & EAV Design

The target table is `celex_facts.facts`, which implements an **Entity-Attribute-Value (EAV)** design:

```sql
TABLE celex_facts.facts (
    celex_id   TEXT,   -- Entity: case identifier (e.g. '38344_5856_3', 'CELEX-31975D0358')
    name       TEXT,   -- Attribute: fact name determining the type/meaning of value_md
    value_md   TEXT,   -- Value (polymorphic text representation)
    value_json JSONB   -- Value (structured JSON representation, optional)
);
```

### Fact Type Mapping
Because `value_md` is polymorphic, queries must handle casting appropriately depending on the `name` column:

| Data Type | Fact Names (`name`) | `value_md` Format | Safe Casting / Filter Pattern |
|---|---|---|---|
| **Boolean** | `leniency_case`, `exemption_case`, `market_outside_eu`, `market_oligopoly`, `is_court_involved`, `case_commission_decision`, `case_commission_no_action`, `case_commission_info_request`, `leniency_case_match`, `infringement_category_abuse_of_dominance`, `infringement_category_procedural`, `infringement_category_member_states` | `'True'` or `'False'` | `name = 'leniency_case' AND value_md = 'True'` |
| **Date** | `eu_commisssion_decision_date` | `'YYYY-MM-DD'` | Requires length/regex guard:<br>`LENGTH(value_md) = 10 AND value_md::date`<br>or `value_md ~ '^[0-9]{4}-[0-9]{2}-[0-9]{2}$'` |
| **Date Range** | `heideltime_cartel_period`, `legal_assessment_period` | `'YYYY-MM-DD : YYYY-MM-DD'` | Text parsing required. |
| **Categories** | `infringement_category_hor_vert_lic_joint`, `infringement_subcategory_horizontal_restraints`, `infringement_subcategory_vertical_restraints`, `infringement_gravity`, `OECD_sector`, `NACE_group_code`, `NACE_class_code` | Short label string | `name = 'OECD_sector' AND value_md ILIKE '%chemical%'` |
| **Free Text / Markdown** | `leniency_applicants`, `fines`, `companies_investigated`, `companies_country`, `company_recidivism`, `case_commissioner`, `case_summary`, `case_title`, `court_list_raw` | Markdown, Tables, or Paragraphs | `name = 'case_commissioner' AND LENGTH(value_md) > 2` |

## 3. SQL Safety & Validation Gate

All SQL generated by the planner is run through a strict safety gate in `_validate_read_only_sql(sql)` prior to execution:

1. **Markdown Fence Stripping:** Auto-detects and removes markdown wrap (e.g. ````sql ... ````).
2. **Comment Stripping:** Safely strips leading SQL line comments (`-- comment`).
3. **Multi-Statement Block:** Blocks query chaining (rejects if `;` is present in the trimmed string).
4. **Statement Type Lock:** Rejects any query that does not start with `SELECT` or `WITH`.
5. **Write Operation Prevention:** Scans query tokens for write-related SQL keywords:
   `INSERT`, `UPDATE`, `DELETE`, `DROP`, `ALTER`, `CREATE`, `TRUNCATE`, `GRANT`, `REVOKE`.
6. **Limit Enforcement:** Automatically appends `LIMIT 500` if no `LIMIT` clause is specified in the query.

## 4. Execution & Case Title Auto-Enrichment

The `_ToolDispatcher._run_kb_sql(query)` method controls execution:

```python
def _run_kb_sql(self, query: str) -> str:
    safe_sql = _validate_read_only_sql(query)
    rows = self.aggregator.aggregate_facts(safe_sql)
    if not rows:
        return "[kb_sql] No rows returned."
    rows = self._enrich_with_case_titles(rows)
    lines = [str(r) for r in rows]
    return "[kb_sql] " + "\n".join(lines)
```

### Protocol Injection
Execution is decoupled from the underlying database driver using the `CrossCaseAggregator` protocol:
```python
class CrossCaseAggregator(Protocol):
    def aggregate_facts(self, sql: str) -> list[dict]:
        ...
```
A concrete implementation (`FactAggregator`) connects to PostgreSQL using SQLAlchemy:
```python
class FactAggregator:
    def __init__(self, engine) -> None:
        self.engine = engine

    def aggregate_facts(self, sql: str) -> list[dict]:
        with self.engine.connect() as conn:
            result = conn.execute(text(sql))
            columns = list(result.keys())
            return [dict(zip(columns, row)) for row in result.fetchall()]
```

### Auto-Enrichment
If the database output rows contain a `celex_id` key, the dispatcher:
1. Gathers all unique `celex_id` values from the rows.
2. Resolves their titles (`case_title`) using the SQL store (`sql_store.select_fact4celex(cid, "case_title")`).
3. Appends a new key-value pair `"case_title": "<resolved title>"` to each row.

This ensures that the final response synthesizer receives human-readable case names (e.g. `celex_id — case title`) rather than just raw alphanumeric identifiers.

## 5. Fact-Name Fallback Mechanism

If the planner generates malformed SQL or returns zero rows, the execution module triggers a fallback mechanism called **Fact-Name Fallback** inside the `QAExecutorModule`:

1. It parses the user's natural language question for any token that matches:
   * Explicit underscore-separated names (e.g. `court_list_raw`, `NACE_group_code`).
   * Canonical fact names resolved from question synonyms (e.g. "summary" maps to `case_summary`).
2. If any fact-name candidate is identified, it executes a fallback query:
   ```sql
   SELECT celex_id, value_md 
   FROM celex_facts.facts 
   WHERE name = '<matched_fact_name>' 
   LIMIT 500
   ```
3. If this fallback query returns rows, the executor appends it to the evidence context under:
   `--- Fallback (fact_name -> <matched_fact_name>) ---`

This fallback guarantees that cross-case questions mentioning specific facts always return structured data even if the LLM fails to construct a valid SQL query.
